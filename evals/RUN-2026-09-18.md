# Three-condition run, 2026-09-18

Follow-up to the [pilot](PILOT-2026-09-18.md): all 14 cases, three conditions,
five planned repetitions. **Still not a benchmark.** It is one model, one host,
a small Python fixture set, incomplete cells, and an unblinded reviewer. Read the
limitations before quoting any number.

## Setup

Same agent, model, isolation, and tools as the pilot: Claude Code 2.1.258 in
headless `claude -p`, `claude-opus-5` at default effort, a fresh session per run
in a workspace copy outside the repository, no skill installed in the host.
The `skill` condition supplies `SKILL.md` in the prompt.

210 runs were planned. **27 ended with HTTP 429 (account monthly spend limit)**,
some partway through a task. They say nothing about agent behavior, so they are
excluded rather than counted as agent failures. They were not rerun, to limit
cost. That leaves **183 valid runs**: 60 baseline, 62 one-line, 61 skill. Cells
have 2–5 runs; see the table below.

Line counts below use the corrected `inspect` diff, which ignores line-ending-only
changes. Before that fix, 9 runs whose editor rewrote a test file with CRLF
endings were reported as adding up to 16 test lines when they added 1–3.

## What the runs did

- **Seven restraint cases did not discriminate.** For 01, 02, 03, 04, 06, 08,
  and 10, every valid run in every condition produced a byte-identical diff.
  This model reused existing coverage on mechanical changes without any
  instruction, fixed prose without adding tests, and reused case 06's existing
  failing regression.
- **12 and 14** added the one requested or required test in every run.
- **05:** every run fixed the boundary and added boundary coverage. All five
  baseline runs also added a past-expiry test that the boundary test already
  makes unnecessary for this bug (5 redundant additions).
- **09:** three of five baseline runs added a test calling
  `parse_limit(raw="7")`, freezing the renamed parameter as a keyword-argument
  contract that the task did not authorize (3 invented requirements, also counted
  as redundant). No one-line or skill run did this.
- **11:** 9 of 10 valid runs changed nothing and asked which behavior
  "gracefully" should mean, citing the README's statement that none is agreed.
  One baseline run instead chose a clearer `ValueError` and added a test
  freezing it, then flagged the choice afterward. That counts as an incorrect
  task outcome and an invented requirement under the rubric.
- **13 is the only case separating one-line from skill.** The task introduces a
  public key and a precedence rule including zero. All five baseline runs covered
  the new key alone, non-zero precedence, and zero-valued precedence. All four
  one-line runs added a single assertion covering only zero-valued precedence,
  leaving use of the new key without the legacy key untested. Four of five skill
  runs covered both the new key alone and zero-valued precedence; one matched
  the one-line pattern. The acceptance subset passes in every case, so this is
  thinner contract coverage, not a failing behavior.

## Reading

On this model, both instructions removed baseline's excess: 8 redundant
additions and 4 invented requirements, including the one wrong answer on the
ambiguity case, became zero, with no loss of correctness or existing
protection. Mean added test lines fell from 2.48 to 1.16 (one-line) and 1.33
(skill).

The one-sentence instruction was as effective as the full skill at restraint.
The only observed difference is case 13: the one-line runs cut coverage below
the contract the task defines in 4 of 4 runs; the skill runs did so in 1 of 5.
That is the behavior the skill is designed for (keep necessary contract
coverage while cutting ceremony), but it rests on nine runs of a single case.
Treat it as a hypothesis to test with more contract-changing cases, not as a
finding.

The skill costs about 19% more per run on these tiny tasks, mostly from the
skill text in the prompt. On real tasks the fixed prompt cost would be a much
smaller share.

## Limitations

- One model (`claude-opus-5`) and one host. This model is a strong baseline:
  it already showed restraint on mechanical changes, so the restraint cases had
  no room to show an effect.
- 27 of 210 runs were lost to a spend limit and not rerun. Cells are unbalanced
  (07 baseline has only 2 runs, 11 baseline 3).
- No statistics were computed; with these counts, confidence intervals would be
  wide enough to include no effect.
- Reviewed by the agent that ran the harness, knowing each run's condition. A
  blind independent review would be better.
- The `skill` condition measures the skill's content when loaded, not host
  discovery or automatic activation.
